# Anklang

`make check` fails when a file, make target or class name in backticks below stops existing.

## Where code goes
- `trkn/` is Tracktion Engine and JUCE, vendored. Patches there are build or integration fixes, one file per commit. Anklang features go in `ase/` and use Tracktion.
- A `.cc` file that uses Tracktion or JUCE includes `trkn/tracktion.hh` or `trkn/juce.hh` first, for the precompiled header. Headers don't include them; they use the forward declarations from `ase/trkn.hh`.
- `ase/api.hh` is the whole IPC interface.
- Files with `.g.` in the name are generated by `make`. Never edit them.
- Apart from connection setup in `ui/startup.js`, `ui/` talks to the engine only through the classes in `ase/gen/api-jsonipc.g.ts`.
- UI components get the project from `Shell.project`, not `App.project`.
- Sources in `devices/` that `devices/Makefile.mk` doesn't build use the removed engine. They wait to be ported. Don't copy from them.

## Project state
- Project data lives in the Tracktion `Edit`. Don't keep copies in `ase/` members; undo and saving miss them.
- Change Tracktion state through its API, e.g. `track->setHidden (true)`, never with `state.setProperty (...)`.
- Tracktion calls that take an `UndoManager*` get the edit's undo manager for project data, never `nullptr`.
- In `ase/`, every change to a property's value emits `notify:<prop>`, whatever caused it: setter, undo, redo or load. The Tracktion state listeners of `ProjectImpl`, `TrackImpl`, `ClipImpl` and `PluginImpl` send it.
- To expose a Tracktion property, add a `foo()` and `foo (v)` pair to `ase/api.hh`, implement both in the `*Impl` class with the Tracktion API, and map its `IDs::` entry to `emit_notify ("foo")` in the class's state listener.
- In `ui/`, read properties from the Ase proxy objects. They start as 0, "" or [] and update by themselves. Don't subscribe to `notify:` for properties.

## Code
- Use GNU style and snake_case wherever possible. Write casts as `int64_t (x)`, not `(int64_t) x`.
- Use `ase/regex.hh`, not `std::regex`, and add a helper there if one is missing. Prefer `ase/path.hh` over `std::filesystem`.
- Debug output uses `debug ("<key>", ...)`. `printout` is for deliberate output only.
- Remove code that has no callers.

## Removing code
- Odd or complex code usually handles a real problem. Before you remove or rewrite it, find out why it's there: `git log -L`, commit messages, bug trackers, release notes, other projects. Reproduce the problem where you can.
- A commit that removes logic has an `Evidence:` paragraph: why the code was added and why it's no longer needed, with commit ids or links. `make check` fails when a commit deletes a block of 10 or more lines of code and puts nothing in its place, unless it has an `Evidence:` paragraph.
- If you are unsure, ask. If you can't wait for the answer, start the first line with `**REVIEW**: `.
- Never remove code just to make a check pass. Exempt it from the check instead.

## Checks
- `make` builds. `make check` runs `make lint`, `ase/tests/` and `ui/tests/`.
- Every behavior change needs a test. Prefer C++ tests in `ase/tests/`. Use `ui/tests/` for UI behavior only.
- Tests use the `ase/api.hh` interfaces, not Tracktion directly. Don't test what the type system already guarantees.
- UI tests wait for the event that really happens, usually the next frame. Never wait a fixed time.
- Support the last 3 versions of Chrome and Firefox. Don't add vendor prefixes, fallbacks or browser-version checks for older ones.
